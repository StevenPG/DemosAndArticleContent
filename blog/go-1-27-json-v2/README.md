# Go 1.27 encoding/json/v2 — Behaviour, Benchmarks, and the Migration

Companion project for the blog post
[Go 1.27's encoding/json/v2: You Already Upgraded](https://stevenpg.com/posts/go-1-27-encoding-json-v2/).

Go 1.27 (2026-08-19) graduated `encoding/json/v2` and `encoding/json/jsontext`
out of `GOEXPERIMENT=jsonv2`. The part that affects you whether or not you opt
in: **`encoding/json` is now implemented on top of v2.** You inherit the new
engine the moment you build with 1.27.

This project answers three questions with running code:

1. What actually changes when you keep importing `encoding/json`? (Nothing
   semantic — verified.)
2. What changes when you import `encoding/json/v2` instead? (Six differences,
   each verified and each with the option that pins it back.)
3. Is it faster? (Yes on unmarshal, everywhere. Mostly parity on marshal, with
   two exceptions worth knowing.)

## Requirements

- **Go 1.27+**. The module pins `toolchain go1.27.1`, so an older `go` command
  downloads the right toolchain automatically. No dependencies.
- `benchstat` for the comparison table:
  `go install golang.org/x/perf/cmd/benchstat@latest`

## Quick start

```bash
make            # vet, test, then print the difference report
make report     # the v1-vs-v2 difference table, generated by running both
make bench      # full benchmark sweep, -count=10, ~6 minutes
make benchstat  # render the comparison
```

## What's here

| Package | Purpose |
|---|---|
| `internal/differences` | Every behavioural difference found between v1 and v2, as a table-driven catalogue. Each case runs **both** packages and asserts they still differ — if a future Go release changes one, the test fails instead of the blog post quietly going stale. |
| `internal/options` | Four migration profiles: legacy (behaviour no-op), interop, strict, and security. |
| `internal/streaming` | What `jsontext` makes possible: redacting fields from a document whose shape you do not know, without unmarshaling it. |
| `bench` | Five-shape benchmark corpus, generated deterministically from a fixed seed. |
| `results/` | Committed raw output, benchstat tables, and methodology. |

## The six differences

Generated by `make report`, observed on Go 1.27.1. **Severity `error`** means
v2 fails loudly and you find out at once. **Severity `silent`** means v2
succeeds with different data — audit those first.

| # | Difference | Severity | v1 | v2 |
|---|---|---|---|---|
| 1 | Invalid UTF-8 (marshal) | error | `{"name":"caf�"}` | `jsontext: invalid UTF-8 within "/name" after offset 8` |
| 2 | Invalid UTF-8 (unmarshal) | error | accepts, corrupts | `jsontext: invalid UTF-8 within "/name" after offset 12` |
| 3 | Duplicate object names | error | last one wins | `jsontext: duplicate object member name "name"` |
| 4 | Case-insensitive matching | **silent** | `Name="ada"` | `Name=""` |
| 5 | nil slice / nil map | **silent** | `{"items":null,"attrs":null}` | `{"items":[],"attrs":{}}` |
| 6 | `time.Duration` | error | `{"timeout":90000000000}` | `no default representation` |

Each has an option that restores v1 behaviour, verified by the test suite:

```go
jsontext.AllowInvalidUTF8(true)       // 1, 2
jsontext.AllowDuplicateNames(true)    // 3
v2.MatchCaseInsensitiveNames(true)    // 4
v2.FormatNilSliceAsNull(true)         // 5
v2.FormatNilMapAsNull(true)           // 5
json.FormatDurationAsNano(true)       // 6 -- from encoding/json, not v2
```

Or restore all of them at once with `json.DefaultOptionsV1()`.

### The two that will actually bite you

**Case-insensitive matching (#4)** is the dangerous one because it is silent. v1
fell back to case-insensitive matching of object names; v2 is case-sensitive. A
producer sending `"userId"` against a `json:"userid"` tag used to work and now
yields a zero value, with no error anywhere.

**`time.Duration` (#6)** is the one that stops your build dead. v1 emitted the
nanosecond count because `Duration` is an `int64` underneath. v2 refuses to
guess a representation and errors, so *any* struct carrying a `time.Duration`
fails to marshal under plain v2.

## Benchmarks

Full tables and caveats in [results/README.md](results/README.md). Headline,
`benchstat -col /impl`, `-count=10`, Go 1.27.1 on a 4-core Xeon:

```
                     │      v1      │                 v2                  │
                     │    sec/op    │   sec/op     vs base                │
Marshal/Small           649.0n ± 3%   679.2n ± 6%        ~ (p=0.353 n=10)
Marshal/Nested          6.676µ ± 5%   7.024µ ± 2%   +5.21% (p=0.004 n=10)
Marshal/Batch           917.9µ ± 4%   921.6µ ± 3%        ~ (p=0.393 n=10)
Marshal/Document        48.83µ ± 1%   48.94µ ± 3%        ~ (p=0.393 n=10)
Marshal/Dynamic         86.61µ ± 2%   60.01µ ± 5%  -30.71% (p=0.000 n=10)
Unmarshal/Small        1061.5n ± 2%   855.7n ± 3%  -19.39% (p=0.000 n=10)
Unmarshal/Nested        14.47µ ± 4%   13.19µ ± 9%   -8.80% (p=0.000 n=10)
Unmarshal/Batch         2.071m ± 5%   1.743m ± 8%  -15.86% (p=0.000 n=10)
Unmarshal/Document     119.50µ ± 2%   86.97µ ± 5%  -27.22% (p=0.000 n=10)
Unmarshal/Dynamic      147.77µ ± 4%   95.46µ ± 4%  -35.40% (p=0.000 n=10)
geomean                 39.58µ        34.07µ       -13.92%
```

Unmarshal is faster on every shape. Marshal is at parity on three of five —
with `map[string]any` **30.7% faster** (and half the allocations), and deeply
nested marshal **5.2% slower**, which is small but statistically real and is not
mentioned upstream.

## What `jsontext` unlocks

`internal/streaming` redacts named fields from a document whose schema you do
not model, one token at a time. Memory stays proportional to nesting depth and
the largest scalar, not to document size.

The property that makes it worth using is numeric fidelity. Values are copied
as raw text, so nothing is round-tripped through `float64`:

```
input:      "raw_precision": 1.7976931348623157e308,  "big_int": 123456789012345678901234567890

jsontext:   "raw_precision": 1.7976931348623157e308,  "big_int": 123456789012345678901234567890
map[string]any round-trip:
            "raw_precision": 1.7976931348623157e+308, "big_int": 1.2345678901234568e+29
```

The `map[string]any` path destroyed the big integer. The token stream did not.

v2 errors also carry a **JSON Pointer to the exact fault location**, extracted
with `errors.AsType` (itself new in 1.27):

```
at /items/1/name (member "name"): duplicate object member name
```

## The escape hatch

`GOEXPERIMENT=nojsonv2` restores the original v1 implementation. It is
explicitly temporary and expected to be removed, so it buys you a release to
fix things — not a strategy.
