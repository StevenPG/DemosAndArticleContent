# Go 1.27 Generic Methods — What They Fix, and What They Still Don't

Companion project for the blog post
[The Ultimate Guide to Go 1.27 Generic Methods](https://stevenpg.com/posts/ultimate-guide-go-1-27-generic-methods/).

Go 1.27 (released 2026-08-19) lets a **method** declare its own type parameters:

```go
func (s *Source) Get[T any](key string) (T, error)
```

Before 1.27, a method could use its *receiver's* type parameters but never
declare its own. That single restriction is why so much Go code carries a family
of near-identical typed methods, or falls back to `any`.

This project shows where that genuinely helps, where it doesn't, and it
**compiles the illegal cases to capture the compiler's real error messages** —
nothing in the post is paraphrased.

## Requirements

- **Go 1.27+**. The module pins `toolchain go1.27.1`, so an older `go` command
  downloads the right toolchain automatically. Nothing else is needed; the
  module has no dependencies.
- One gotcha: a `gofmt` binary on your `PATH` from an earlier Go **cannot parse
  generic methods** and will report `method must have no type parameters`. Use
  `make fmt`, which invokes the pinned toolchain's own copy.

## The three restrictions, verified

`go test ./internal/limits/ -v` compiles each case and asserts the compiler
rejects it. Actual output from Go 1.27.1:

**1. An interface method may not declare type parameters.**

```
./p.go:6:5: interface method must have no type parameters
```

This is the wall. The port you want to write — `Repository` with a generic
`Get[T]` — is still illegal, so the headline "generic methods simplify clean
architecture" needs an asterisk. See `internal/ports` for what to do instead.

**2. A generic method does not satisfy a non-generic interface method.**

```
./p.go:16:15: cannot use PostgresStore{} (value of struct type PostgresStore) as
Store value in variable declaration: PostgresStore does not implement Store
(wrong type for method Get)
		have Get[T any](string) (T, error)
		want Get(string) (any, error)
```

**3. An uninstantiated generic method has no single func type.**

```
./p.go:9:9: cannot use generic function Encoder{}.Encode without instantiation
```

(Note the compiler says "generic function" even for a method.) Instantiate it
first and it becomes an ordinary method value: `var f func(string) (int, error) = s.Get[int]`.

## The rule this project argues for

> Parameterize the **type** when `T` is part of the value's identity — the
> receiver genuinely *is* a container of `T`, and two instances with different
> `T` should share nothing.
>
> Parameterize the **method** when `T` varies per call against receiver state
> that is deliberately **shared** across every `T`.

`internal/cache` makes the second case concrete. A `Cache[T]` forces one
instance per value type — a `Cache[User]`, a `Cache[Session]` — each with its
own memory budget and eviction clock. A burst of `User` traffic then cannot
reclaim memory from cold `Session` entries, which is the entire point of a
shared cache. Splitting by type isn't a typing detail; it breaks the eviction
semantics. That design needed a generic method, and before 1.27 it could only
be spelled as a package-level `GetAs[T](c *Cache, key string)`.

`internal/cache/typed.go` shows the opposite case — a ring buffer really is a
buffer of one type — plus the two composing: a generic method on a generic type.

## Real-world scale of the problem

Generated by `internal/stdlib` (the flag count via reflection, at runtime):

- **`flag.FlagSet`: 16 methods** — `Bool`, `BoolVar`, `Int`, `IntVar`, `Int64`,
  `Int64Var`, `Uint`, `UintVar`, `Uint64`, `Uint64Var`, `Float64`, `Float64Var`,
  `String`, `StringVar`, `Duration`, `DurationVar` — one idea, eight types, two
  shapes each.
- **`github.com/spf13/viper`: 19 typed `Get*` accessors** on one type.
- **`sync.Map`, `sync/atomic.Value`, `context.Context`**: return bare `any`
  because the method could not be generic.

None of these can change — the Go 1 compatibility promise makes the families
permanent. Generic methods are for the APIs written from here on.

## The stdlib's own adoption

`math/rand/v2` gained a generic method in 1.27:

```go
func           N[Int intType](n Int) Int   // package-level, since 1.22
func (r *Rand) N[Int intType](n Int) Int   // method, new in 1.27
```

Verified in `internal/stdlib/stdlib_test.go`, including inference (`r.N(100)`),
explicit instantiation (`r.N[uint32](50)`), and named types (`r.N[Port](1024)`).
