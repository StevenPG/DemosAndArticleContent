# Docker Jar Packaging Benchmark

Ten ways to put the same Spring Boot application into a container image, built
and measured side by side: fat jar, JRE base, Spring Boot layered jar, extracted
jar, AppCDS, JDK 25 AOT cache, `jlink` custom runtimes, Alpine/musl and
distroless.

Accompanies the post **[Ten Ways to Dockerize a Spring Boot Jar, Measured](https://stevenpg.com/posts/docker-jar-packaging-benchmark/)**.

Measured per variant:

- cold build time and rebuild time after a one-line code change
- compressed (pull) and uncompressed (on-disk) image size
- how many bytes a one-line code change forces a node to re-pull
- time from `docker run` to the first served HTTP request, five runs
- classes loaded at startup
- container memory at idle and under load
- throughput, p50 and p99 under a 20 second, 16 thread load

## Layout

```
bench-app/          the application - Spring Boot 4.1, JDK 25, ~250 classes of
                    generated domain code on top of MVC + JPA + security
docker/             one Dockerfile per packaging variant, numbered 01..10
scripts/            benchmark harness and the domain code generator
results/            raw.json and results.md, regenerated by the harness
```

Every Dockerfile shares a byte-for-byte identical build stage, so nothing in the
results comes from building the application differently - only from how the
output is packaged and started.

## The application

A read-heavy "fleet telemetry" API. Nothing about it is clever; the point is
that it is *big enough to be representative*:

- Spring Boot 4.1 on JDK 25 (webmvc, data-jpa, validation, security, actuator)
- 24 generated domain packages, 10 classes each - entity, enum, repository,
  projection, DTO, event, mapper, service, controller, seeder
- ~250 application classes, ~90 dependency jars, a 60MB fat jar
- ~18,700 classes loaded by the time the context is ready

The domain packages are generated by `scripts/generate-domains.py` and committed.
Regenerate with:

```bash
python3 scripts/generate-domains.py bench-app/src/main/java
```

## Running the benchmark

Requires Docker with BuildKit and Python 3.11+. Nothing else - the JDK comes from
the build images.

```bash
# everything: build, measure, report
python3 scripts/benchmark.py all

# or step by step
python3 scripts/benchmark.py build
python3 scripts/benchmark.py measure --runs 5 --load-seconds 20 --threads 16
python3 scripts/benchmark.py report

# one variant at a time
python3 scripts/benchmark.py --only 06-extracted-aot build
```

Results land in `results/raw.json` (every sample) and `results/results.md`
(the rendered tables).

### Offline / air-gapped builds

Dependency downloads are network-bound and would add more jitter than the effects
being measured, so the published numbers were produced against a pre-seeded
builder image:

```bash
cd bench-app && ./gradlew bootJar && cd ..   # populate ~/.gradle
./scripts/seed-builder-image.sh              # bake it into jarbench:builder
python3 scripts/benchmark.py build --offline # build against it, Gradle --offline
```

The same two build args work by hand and are the mechanism you would use in an
air-gapped environment:

```bash
docker build \
  --build-arg BUILD_IMAGE=jarbench:builder \
  --build-arg GRADLE_ARGS=--offline \
  -f docker/06-extracted-aot.Dockerfile -t jarbench:06 .
```

Both default to the stock public image and an online build, so a plain
`docker build -f docker/01-fatjar-jdk.Dockerfile .` works with no arguments.

## Building a single variant by hand

```bash
docker build -f docker/09-jlink-alpine.Dockerfile -t jarbench:09 .
docker run --rm -p 8080:8080 --memory 1g --cpus 2 jarbench:09
curl localhost:8080/actuator/health
curl localhost:8080/api/aircraft/stats
```

## The variants

| File | What it does |
|---|---|
| `01-fatjar-jdk.Dockerfile` | Fat jar copied onto the full JDK image. The baseline. |
| `02-fatjar-jre.Dockerfile` | Same, on the JRE image. One-word diff. |
| `03-layered.Dockerfile` | `jarmode=tools extract --layers --launcher`, one COPY per Boot layer. |
| `04-extracted.Dockerfile` | `jarmode=tools extract` - thin jar plus `lib/`, no nested-jar loader. |
| `05-extracted-cds.Dockerfile` | Extracted, plus an AppCDS archive trained at build time. |
| `06-extracted-aot.Dockerfile` | Extracted, plus a JDK 25 AOT cache (`-XX:AOTCacheOutput`). |
| `07-jlink-fatjar.Dockerfile` | `jdeps` + `jlink` runtime on `debian:trixie-slim`, fat jar. |
| `08-jlink-extracted-aot.Dockerfile` | jlink runtime + extracted jar + AOT cache trained *with the jlink runtime*. |
| `09-jlink-alpine.Dockerfile` | jlink built in the Alpine JDK image (musl), shipped on Alpine. |
| `10-jlink-distroless.Dockerfile` | jlink runtime on `gcr.io/distroless/base-debian13`. |

## Notes and gotchas

- **CDS and AOT caches record their classpath.** Train from the same absolute
  paths the container will use at runtime, or the JVM silently ignores the
  archive. Check with `-Xlog:aot` / `-Xlog:cds` - you want to see
  `Opened AOT cache`, not a fallback message.
- **An AOT cache is tied to the exact `java` binary.** Variant 08 trains with the
  jlink runtime rather than the build JDK for exactly this reason.
- **`jdeps` cannot see reflection.** `jdk.crypto.ec`, `jdk.management` and
  `jdk.localedata` are added explicitly; `--ignore-missing-deps` is mandatory
  because Spring's optional integrations reference classes that are not on the
  classpath.
- **Training runs use `-Dspring.context.exit=onRefresh` and `bench.seed.rows=0`**
  so the build stage starts the context, records the cache and exits without
  writing seed data.
